## 1 · გეგმა (კოდი არა) — და დადასტურების ლოდინი

დაწერე გეგმა ამ სათაურებით:

- **ინვარიანტი** — რა არის ფუნქციის ერთადერთი ინვარიანტი
- **ჩავარდნები და კიდეური შემთხვევები** — რა შეიძლება ცუდად წავიდეს (დუბლიკატი, ერთდროული მოთხოვნა, timeout, გამეორებული callback, დღის საზღვარი Asia/Tbilisi)
- **მოთხოვნები და ინდექსები** — რომელი ეკრანი/endpoint რას კითხულობს; რა composite ინდექსი გვჭირდება; სად შეიძლება ორმა მოთხოვნამ ერთდროულად ჩაწეროს
- **მფლობელი მოდული** — რომელი მოდული ფლობს მონაცემს; სხვა მოდულთან მხოლოდ index.ts-ით
- **პატერნები** — რომელი პატერნი კატალოგიდან (create-only ID, state machine, job, ledger, policy ფუნქცია …)
- **OpenAPI ცვლილება** — მხოლოდ დამატებით; რა გენერირდება
- **განმარტება თუ ძრავა** — რა არის ცვალებადი წესი (definition/config, ვერსიით) და რა — ძრავა
- **საჭიროა თუ არა ADR** (ახალი სერვისი/ბიბლიოთეკა/პატერნი/მოდული, ან პრინციპიდან გადახვევა)
- **დაშვებები** — რას ვვარაუდობ (დაშვება ≠ ფაქტი)
- **ღია კითხვები** — რაც განმარტებაში არ წერია; ჩაწერე „ღიაა“ (#-ნომრით, თუ არსებობს `docs/open-questions.md`-ში) და ისე შემოგვთავაზე კონფიგურაცია ან ერთი წესი-ფუნქცია, რომელიც ორივე პასუხს უძლებს

**შეჩერდი. არ დაიწყო კოდი, სანამ მფლობელი გეგმას არ დაადასტურებს.** თუ გეგმა პრინციპს ეწინააღმდეგება — ეს გადახვევაა: შეჩერდი და იკითხე.

## 2 · შესრულება (დადასტურების შემდეგ)

1. **ტესტები ჯერ.** ინვარიანტის ტესტები არ არის დამოკიდებული განმარტებაზე; policy ტესტები პარამეტრიზდება. ფული და ჯავშანი — property-based, ერთდროული მოთხოვნა, დუბლიკატი.
2. **კოდი პატარა ნაბიჯებით** (use case = ერთი ტრანზაქცია; ჯერ წაკითხვა, მერე ჩაწერა; გარე ზარი მხოლოდ job-ით / adapter-ით).
3. **გეიტები:** `pnpm gates` (format, lint, typecheck, architecture, tests, api contract), `pnpm test:integration` (Emulator Suite, rules, ინდექსები), e2e კრიტიკულ გზაზე. გეიტი წითელია → არ გადახვიდე მომდევნო ნაბიჯზე.
4. **სარისკო ცვლილება** — kill switch-ით; გატეხილი ცვლილება — expand → deploy → migrate → contract.
5. თუ გადაწყვეტილება არაცხადია ან გადაუხვიე რეკომენდაციას — ჩაწერე ADR (`docs/adr/`).
