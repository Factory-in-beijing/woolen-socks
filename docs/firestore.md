# Firestore ბლოკი — ჩასაკოპირებელი

_NoSQL-ის წესები რატომ-ებით — ერთ გვერდზე._

> წყარო: „DriveNet 2027 · არქიტექტურა და სამუშაო წესები“ v6, გვ. 6. ტექსტი წყაროდანაა გადმოღებული ცვლილების გარეშე.

> Firestore ბლოკი — ბექენდის ყოველ პრომპტში, 27 პრინციპის შემდეგ.
>
> Firestore — ყოველ ფუნქციაზე, რომელიც მონაცემს ეხება
>
> ჩასაკოპირებელი · ბექენდი

## როგორ გამოიყენო

- ეს ბლოკი ინჟინერიული ბაზაა — ის განსაზღვრავს, როგორ ვაშენებთ და არა რას. ხელით ჩაწერილი განმარტება (ფუნქცია, მოთხოვნები, შემთხვევები) ყოველთვის მთავარია და ბაზით არ იზღუდება. თუ განმარტება რეკომენდაციას ეწინააღმდეგება — მიჰყევი განმარტებას და ანგარიშში ჩაწერე, რა შეცვალე და რატომ. თუ ეწინააღმდეგება პრინციპს (1–27) — შეაჩერე და მკითხე.
- Firestore NoSQL-ია: join, unique constraint და ad-hoc მოთხოვნა არ არის. ამიტომ მონაცემს წაკითხვისა და ერთდროულობის სცენარიდან ვაპროექტებთ. გეგმაში ჯერ ჩაწერე: რა მოთხოვნები გვჭირდება, რომელი დოკუმენტი ფლობს მონაცემს, რა ინდექსია საჭირო, სად შეიძლება ორმა მოთხოვნამ ერთდროულად ჩაწეროს.

## მოდელი

- მოთხოვნიდან დაიწყე: ერთი ეკრანი/endpoint = ერთი წაკითხვა (ერთი დოკუმენტი ან მცირე ჯგუფი). რატომ: join არ არის, ბევრი მცირე წაკითხვა ნელი და ძვირია.
- რაც ერთად იცვლება და იკითხება — ერთ დოკუმენტში; რაც იზრდება (ისტორია, ჟურნალი) — ცალკე დოკუმენტებად; დოკუმენტი < 1 MiB. რატომ: ზომის ლიმიტი და ჩაწერის კონკურენცია.
- წაკითხვისთვის დენორმალიზება (მაგ. ინსტრუქტორის ბარათი): წყარო ცალკეა და ჭეშმარიტებაა; ასლს job ანახლებს და აქვს rebuild. რატომ: სწრაფი სია, მაგრამ ასლი ყოველთვის აღდგება.
- collection: root collection + მფლობელის ველი (workspaceId/personId); subcollection — მხოლოდ თუ ჩანაწერი მშობლის გარეშე არ იკითხება. მოდული ფლობს თავის collection-ებს. რატომ: cross-workspace მოთხოვნები (ადმინი, მარკეტპლეისი) მარტივია.

## ID და ერთდროულობა

- „ერთხელ“ ან „უნიკალური“ → განსაზღვრული ID + create-only (slot = პირი+თარიღი+უჯრა; payout = lessonId; სივრცე = applicationId); სხვა შემთხვევაში auto-ID. რატომ: unique constraint არ არსებობს.
- თანმიმდევრული/დროზე დალაგებული ID ან indexed ველი ცხელ ჩაწერაზე არ გამოიყენო. რატომ: მონოტონურ ინდექსზე ჩაწერა ≈ 500/წმ-მდეა.
- ტრანზაქცია: ჯერ ყველა წაკითხვა, მერე ჩაწერა; პატარა; გარე ზარი შიგნით არასდროს; განახლებისას version/precondition → 412. რატომ: კონფლიქტზე ტრანზაქცია თავიდან სრულდება.
- ერთ დოკუმენტზე ხშირ ჩაწერას (მრიცხველი, „ბოლო მდგომარეობა“) ერიდე — გაანაწილე ან დააბათჩე. რატომ: ერთი დოკუმენტი ჩაწერის ვიწრო ადგილია.

## წაკითხვა

- სია: limit + cursor (startAfter), offset არა; დალაგების ველი ინდექსშია. ინდექსები კოდშია (firestore.indexes.json) + ტესტი; ფილტრის კომბინაციები წინასწარ დაგეგმე. რატომ: ინდექსის გარეშე მოთხოვნა ვარდება.
- ჯამი/რაოდენობა: Firestore aggregation (count/sum) ან job-ით rollup; ბევრი დოკუმენტის წაკითხვა ჯამისთვის — არა. რატომ: ყოველი წაკითხვა ფასიანია.

## სიცოცხლის ციკლი

- სქემა: schemaVersion; ახალი ველი ოფციური + default; მკითხველი უცნობ ველს უშვებს; მიგრაცია — იდემპოტენტური სკრიპტი (expand → migrate → contract). რატომ: განმარტება იცვლება, ძველი ჩანაწერი რჩება.
- დროებითი მონაცემი (hold, კოდი, deliveries) — TTL policy; ისტორია (ledger, audit) არასდროს იშლება/იცვლება; backups (PITR) ჩართულია.
- დრო: Timestamp UTC-ში; ბიზნეს-თარიღი ცალკე ველად Asia/Tbilisi-ში.

## უსაფრთხოება და ტესტი

- კლიენტი ბაზას არ ეხება; Rules = deny-all; PII ლოგში არ გადის.
- ტესტი Emulator Suite-ზე (repository, ტრანზაქცია, rules, ინდექსები) mock-ის გარეშე; დატვირთვა — k6.

### დიაგრამები (გვ. 5)

- **დენორმალიზება წაკითხვისთვის:** წყარო (ჭეშმარიტება) → job (ანახლებს ასლს) → listing დოკუმენტი (სია ერთი წაკითხვით) → rebuild job (ასლის აღდგენა).
- **ერთდროულობა: განსაზღვრული ID:** ჯავშნის მოთხოვნა (N უჯრა) → ერთი ტრანზაქცია (create-only slot-ები) → წარმატება (ყველა უჯრა ჩაიწერა) · 409 slot_taken (ერთი დაკავებულია).

**გეგმაში ყოველთვის ჩაწერე:** რომელი მოთხოვნები გვჭირდება · რომელი დოკუმენტი ფლობს მონაცემს · რა ინდექსია საჭირო · სად შეიძლება ორმა მოთხოვნამ ერთდროულად ჩაწეროს · როგორ შეიცვლება სქემა, თუ განმარტება შეიცვლება.
