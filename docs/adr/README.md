# ADR — არქიტექტურული გადაწყვეტილებების ჟურნალი

პრინციპი 26 · **გადაწყვეტილება ჩაწერილია:** არაცხადი არჩევანი და პრინციპიდან გადახვევა ADR-ში იწერება: რა და რატომ. დოკუმენტაცია კოდთან ერთად ახლდება. _რატომ:_ ახალ ადამიანსა და Claude Code-ს შედეგის გარდა მიზეზიც სჭირდება. (Visual Guide, გვ. 4.)

## როდის იწერება ADR

ADR იწერება, როცა:

1. **არაცხადი არჩევანი** კეთდება (პრინციპი 26). მაგალითი წყაროდან: „ტელეფონი + პაროლი“ Firebase Auth-ზე.
2. **პრინციპიდან გადახვევა** გვჭირდება — ვჩერდებით, ვკითხულობთ, ვწერთ ADR-ს (Visual Guide, გვ. 14).
3. **ახალი სერვისი ან ბიბლიოთეკა** ემატება — მხოლოდ ADR-ით (პრინციპი 17).
4. **ახალი პატერნი** ჩნდება კატალოგის გარეთ — მხოლოდ ADR-ით (პრინციპი 17, 26).
5. **ახალი მოდული** ჩნდება — ADR → ფენები და index.ts.
6. **სენიორ-გადაწყვეტილება იცვლება** (მაგ. მიკროსერვისები, API Gateway, Pub/Sub, Load Balancer + Armor) — შეცვლა მხოლოდ ADR-ით (Visual Guide, გვ. 10).
7. **ციფრი (ვადა, ლიმიტი, ზღვარი) უნდა დაფიქსირდეს** და განმარტებაში არ არის: ციფრებს კოდში არ ვწერთ — ისინი ADR-ით განისაზღვრება, როცა პასუხი გვექნება (v6, გვ. 25).

ADR **არ** იწერება ჩვეულებრივ ფუნქციაზე: ახალი ველი/endpoint, use case არსებულ მოდულში, წესის/ვადის/ტექსტის ცვლილება config-ში — ეს თავისუფალია (🟢).

## წყაროში მოხსენიებული მომავალი ADR-ები

ეს გადაწყვეტილებები წყაროში პირდაპირ „ADR“-ად არის დასახელებული და ჯერ **ღიაა**:

- შესვლა ტელეფონი + პაროლით (B1): custom token თუ სინთეტიკური email — Firebase Auth-ს ჩაშენებულად არ აქვს (M1)
- ძველი აპის ვერსიების მხარდაჭერის ვადა
- მობილურის internal build: EAS / Fastlane
- Crashlytics-ის ზღვარი
- ციფრები (ვადები, ლიმიტები, ზღვრები), როცა პასუხი გვექნება
