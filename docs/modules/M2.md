## რეკომენდებული დიზაინი — გადაწყვეტილება და რატომ

- განაცხადი — state machine + სერვერზე შენახული draft; ნაბიჯი = სქემა. რატომ: ნაბიჯები (2/3/4) და მათი შემადგენლობა შეიცვლება; უკან დაბრუნება და სხვა მოწყობილობიდან გაგრძელება უნდა მუშაობდეს.
- დოკუმენტი ცალკე ჩანაწერია სტატუსით; განაცხადის სტატუსი მათგან გამოითვლება. რატომ: უარყოფილი დოკუმენტის ჩანაცვლება არ ეხება დანარჩენს.
- ფაილი — signed URL პირდაპირ Storage-ში; ბაზაში მხოლოდ მისამართი და მეტა. რატომ: API-ს არ ვტვირთავთ; პირადობის/მოწმობის ფაილი ცალკე დაცულია.
- დამტკიცება — workspace + membership + package ერთ Firestore ტრანზაქციაში, ID = applicationId. რატომ: ერთი ბაზაა, ამიტომ Saga არ გვჭირდება; განმეორებით დამტკიცება უვნებელია.
- წევრის აქტივაცია — invite ჩანაწერი ტელეფონით: pending → claimed | rejected. რატომ: „ეს შენი პროფილია?“ (B4) და „არა“ (#11) ორივე ვარიანტს უძლებს.
- მანქანა და პაკეტის ცვლილება — pending, დადასტურებამდე არ მოქმედებს. კონტრაქტი რეგისტრაციის მონაცემებიდან — უცვლელი snapshot + hash. რატომ: ადმინის დადასტურება (M8) და იურიდიული დოკუმენტის სიმტკიცე.
