# BE ბაზა — ჩასაკოპირებელი პრომპტი

_ფენები, API, შეცდომები, job-ები, განმარტება, ტესტები — რატომ-ებით._

> წყარო: „DriveNet 2027 · არქიტექტურა და სამუშაო წესები“ v6, გვ. 15. ტექსტი წყაროდანაა გადმოღებული ცვლილების გარეშე.

> BE ბაზა — ბექენდის ყოველ პრომპტში, 27 პრინციპისა და Firestore ბლოკის შემდეგ.

## როგორ გამოიყენო

- ეს ბლოკი ინჟინერიული ბაზაა — ის განსაზღვრავს, როგორ ვაშენებთ და არა რას. ხელით ჩაწერილი განმარტება (ფუნქცია, მოთხოვნები, შემთხვევები) ყოველთვის მთავარია და ბაზით არ იზღუდება. თუ განმარტება რეკომენდაციას ეწინააღმდეგება — მიჰყევი განმარტებას და ანგარიშში ჩაწერე, რა შეცვალე და რატომ. თუ ეწინააღმდეგება პრინციპს (1–27) — შეაჩერე და მკითხე.

## სტრუქტურა და ფენები

- modules/<name>/{domain,application,infrastructure,http}: controller (http, ვალიდაცია) → use case (application, ერთი ტრანზაქცია) → domain (სუფთა TypeScript, წესები) → repository (port) → Firestore (infrastructure). რატომ: domain ბაზის გარეშე ტესტირდება; Firestore/SDK-ის ცვლილება ერთ ფენას ეხება.
- სხვა მოდულთან — მხოლოდ მისი index.ts; მოდული ფლობს თავის collection-ებს; საზღვრებს lint ამოწმებს. რატომ: ცვლილება ლოკალური რჩება.
- ერთი სერვისი, ერთი deploy; ფონური job-ები იმავე სერვისის /internal/jobs-ზე. რატომ: ამ მასშტაბზე სიმარტივე; გაყოფა მხოლოდ load-ტესტის შემდეგ.

## API

- ჯერ endpoint OpenAPI-ში, მერე კოდი; ტიპები გენერირდება; ცვლილება მხოლოდ დამატებით. Auth: Firebase JWT + can(principal, action, resource); სივრცე: X-Workspace-Id; ყოველი ჩაწერა: Idempotency-Key. რატომ: ერთი კონტრაქტი ვებისთვისაც და მობილურისთვისაც.

## შეცდომები

- AppError → problem+json {code, traceId, retryable}: 400 validation_failed · 401 unauthenticated (ერთნაირი) · 403 forbidden + reason · 404 not_found · 409 slot_taken / hold_expired / invalid_transition · 412 version_mismatch · 429 rate_limited · 503 dependency_unavailable / payment_unavailable (retryable). მოსალოდნელი წარუმატებლობა — მნიშვნელობა, exception — მხოლოდ ბაგი. რატომ: ყველა კლიენტი ერთნაირად რეაგირებს.

## ფონური job-ები

- job = Firestore ჩანაწერი იმავე ტრანზაქციაში, რომელიც ბიზნეს-ცვლილებას წერს → Cloud Tasks (ვადა, retry) ან Cloud Scheduler (პერიოდული, ზონა Asia/Tbilisi) იძახებს handler-ს; handler იდემპოტენტურია; ჩავარდნა → failed + alert. რატომ: SMS/ბანკის გაუმართაობა ბიზნეს-ოპერაციას არ აჩერებს, ჩავარდნა კი არასდროს ჩუმია.

## განმარტება და კონფიგურაცია

- ვადები, ზღვრები, ნაბიჯები, პაკეტის შემადგენლობა, ტექსტები — modules/<name>/definition.ts (declarative) ან config დოკუმენტი (სქემით შემოწმებული, ვერსიული); კოდში გაფანტული რიცხვი არ არის; ჩანაწერზე ინახება გამოყენებული ვერსია. რატომ: განმარტება შეიცვლება — ძრავა და ისტორია უცვლელი უნდა დარჩეს.
- კონფიგურაცია გააკეთე მხოლოდ თუ საკითხი ღიაა (❓) ან უკვე შეიცვალა.

## გარე სისტემები და დაკვირვება

- adapter ყოველ გარე სისტემაზე: timeout; retry მხოლოდ იდემპოტენტურზე; circuit breaker BOG-ზე; ტესტებში fake adapter რეჟიმებით (timeout, დუბლიკატი, გადალაგება). structured ლოგი traceId-ით; alert: ჩავარდნილი job, გადახდის შეცდომა, 5xx; ლოგში PII/ტოკენი/კოდი არა.

## ტესტები

- unit (domain; property-based სადაც წესია) · integration (Emulator Suite, mock-ის გარეშე; ჩავარდნები: დუბლიკატი, timeout, ერთდროული მოთხოვნა) · rules + OpenAPI diff · e2e კრიტიკულ გზაზე · load (k6, 10 000 ერთდროული).
- ინვარიანტის ტესტები განმარტებაზე არ არის დამოკიდებული; policy ტესტები კონფიგით პარამეტრიზდება.

## TypeScript და სუფთა კოდი

- strict, any-ის გარეშე; branded types ფულზე და ID-ებზე; სტატუსი — union; enum-ის ნაცვლად string union; მცირე use case, ერთი პასუხისმგებლობა; დომენის ენის სახელები; კომენტარი „რატომ“, არა „რა“; აბსტრაქცია მხოლოდ განმეორების შემდეგ.

## პროცესი

- ჯერ გეგმა (კოდი არა): რა არის ფუნქციის ერთადერთი ინვარიანტი, რა ჩავარდნები შეიძლება, რა მოთხოვნები/ ინდექსები გვჭირდება, რომელი მოდული ფლობს მონაცემს, დაშვებები და ღია კითხვები. დაველოდე დადასტურებას.
