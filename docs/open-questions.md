# ღია საკითხები (#1–#19) და როგორ ვიქცევით

> წყარო: „DriveNet 2027 · არქიტექტურა და სამუშაო წესები“ v6, გვ. 26 (დანართი: „ნაკადები → მოდულები და ღია საკითხები“), გვ. 13 (#16), და Visual Guide, გვ. 14. ქართული ტექსტი წყაროდანაა გადმოღებული ცვლილების გარეშე.

**წესი (Visual Guide, გვ. 14):** თუ განმარტება ჩუმადაა → ვწერთ „ღიაა“ და ვაბრუნებთ კითხვას, არ ვიგონებთ. არქიტექტურა ორივე პასუხს უძლებს — იცვლება კონფიგურაცია, არა არქიტექტურა.

**წესი (v6, გვ. 26):** 💡 გადაწყვეტილება ღიაა → არ ვაჭედავთ კოდში: კონფიგურაცია, mapping ან ერთი წესი-ფუნქცია. გადაწყდა → იცვლება კონფიგურაცია, არა არქიტექტურა.

**როგორ ვიქცევით პრაქტიკაში** (CLAUDE.md-ის წესების გაგრძელება): ღია საკითხს არ ვწყვეტ ჩუმად. (1) ვწერ „ღიაა“ გეგმაში და ანგარიშში; (2) ვაკეთებ კონფიგურაციას, mapping-ს ან ერთ წესი-ფუნქციას, რომელიც ორივე პასუხს უძლებს; (3) ვაბრუნებ კითხვას მფლობელთან. რიცხვს, ვადას ან ლიმიტს განმარტების გარეშე კოდში არ ვწერ.

### #16 — დანართის ცხრილში არ არის

#16 ნაკადი D-ის გვერდზე (v6, გვ. 13) და D1 ეკრანის სტრიქონშია ნახსენები: „ღია საკითხები: #16 #17 — „+ როლის დამატება“ და შედეგის ეკრანი კონფიგურაციით.“ D1 · PAR-19 მთავარი: შემდეგი გაკვეთილის ბარათი + დღევანდელი განრიგი; როლის გადამრთველი (sheet); ❓ „+ როლის დამატება“.

დანართის ცხრილში #16-ისთვის „არქიტექტურული დაცვის“ ხაზი **არ არის** დაწერილი. ამიტომ: ეკრანი და შემდეგი ნაბიჯი კონფიგურაციით; კონკრეტულ პასუხს არ ვიგონებ — **ღიაა**.

## დოკუმენტში არ არის — მნიშვნელობას არ ვწერთ

(v6, გვ. 25 — გადამოწმებული ფაქტები და ღია ადგილები; ტექსტი წყაროდანაა გადმოღებული ცვლილების გარეშე.)

- გაუქმების და გადატანის ვადა („დროულად“, STU-24/25)
- DriveNet-ის საკომისიო და სიმულაციის ტარიფი (ინვოისი)
- პარტნიორის საბანკო რეკვიზიტები გადარიცხვისთვის (BOnline) — რეგისტრაციის ველებში არ არის
- დაკავების ვადა გადახდის დროს (STU-18 → STU-23)
- ენები (STU-33 „ენის შეცვლა“)
- „დახმარება (Support)“ და „არ გამოცხადდა“-ის გადაწყვეტის პროცესი
- OTP-ის მცდელობები და ვადა (კოდი 6-ნიშნაა — PAR-04)
- სიმულატორის წესები — ცალკე დოკუმენტი (PAR-28), ჯერ არ გვაქვს

### რა არის ჩვენი დიზაინ-გადაწყვეტილება

- მოდულებად დაყოფა (M1–M8), ეკრანის არქეტიპები
- API სტანდარტები, პატერნები, ტესტებისა და საიმედოობის წესები
- Google Cloud / Firebase სერვისების არჩევანი
- ეს პროდუქტის წესი არ არის — ფუნქციები და ეკრანები მხოლოდ ფუნქციურ დოკუმენტსა და ნაკადებს ეყრდნობა
- ციფრებს (ვადები, ლიმიტები, ზღვრები) არ ვწერთ — ისინი ADR-ით განისაზღვრება, როცა პასუხი გვექნება
- 💡 და ❓ ნაკადებში გადაწყვეტილება არ არის

**წყარო:** ფუნქციური დოკუმენტი v2 და „დიზაინის ნაკადები“ (2 ნოე 2026). რაც ამ გვერდზე არ ჩანს — ან ჩვენი დიზაინ-გადაწყვეტილებაა, ან ცნობილი Firebase/Google Cloud შესაძლებლობა, რომელიც ცალკე არ გადამოწმებულა (Cloud Run revisions და traffic split, Cloud Tasks retry და Scheduler time zone, Firestore aggregation (count/sum), Transcoder → HLS, Identity Platform MFA) — პირველი გამოყენებისას დოკუმენტაციით დაადასტურეთ.
