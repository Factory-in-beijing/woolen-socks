## 1. ერთ სურათზე

- **ერთი ბექენდი** (Cloud Run, ერთი სერვისი, მოდულური მონოლითი, stateless, autoscale) ემსახურება ყველა კლიენტს: ვები (სტუდენტი + პარტნიორი), Super Admin, მობილური (მოგვიანებით). კლიენტები იცვლება, ბექენდი — ერთი.
- ტრანსპორტი: `HTTPS /v1 · OpenAPI · Firebase JWT · Idempotency-Key`. სერვერი ფასს, უფლებას, გადახდის შედეგს და გაუქმების პირობას წყვეტს; კლიენტი **მხოლოდ აჩვენებს და აგზავნის მოთხოვნას**.
- ქვემოთ: Firestore (მხოლოდ API-ით, Rules = deny-all, Admin SDK) · Cloud Storage + CDN (signed URL) · Firebase (Auth+Phone, FCM, Crashlytics) · Cloud Tasks + Scheduler (ვადა, retry, Asia/Tbilisi) · Secret Manager/Logging/Monitoring/Cloud Build/Artifact Registry.
- მესამე მხარე adapter-ის უკან: BOG iPay (გადახდა), BOnline (გადარიცხვა), Google Maps, SMS/ელფოსტა, FCM.
- საერთო საფუძველი — ერთი monorepo (TypeScript strict): `api-client` (OpenAPI-დან + TanStack Query), `schemas` (zod), `i18n + tokens` (ტექსტი, Noto Sans Georgian, ერთი formatter Asia/Tbilisi, თეთრი→ლარი), `ui`.
- დიზაინ-პატერნები (სქემის ნომრები): 1 Contract-first · 2 მოდულური მონოლითი · 3 Ports&Adapters · 4 Idempotency · 5 განსაზღვრული ID · 6 Job (ტრანზაქციული რიგი) · 7 State machine · 8 Append-only ledger · 9 განმარტება≠ძრავა · 10 CDN+signed URL.

## 4. Firestore — NoSQL-ის წესები (ყოველ ფუნქციაზე)

join / unique constraint / ad-hoc მოთხოვნა არ არის → ვაპროექტებთ **წაკითხვისა და ერთდროულობის სცენარიდან**. გეგმაში ყოველთვის: რომელი მოთხოვნები გვჭირდება · რომელი დოკუმენტი ფლობს მონაცემს · რა ინდექსია საჭირო · სად შეიძლება ორმა მოთხოვნამ ერთდროულად ჩაწეროს · როგორ იცვლება სქემა, თუ განმარტება შეიცვლება.

- **მოდელი მოთხოვნიდან**: ერთი ეკრანი = ერთი წაკითხვა (ერთი დოკუმენტი ან მცირე ჯგუფი).
- **დოკუმენტის საზღვარი**: რაც ერთად იცვლება და იკითხება — ერთ დოკუმენტში; რაც იზრდება (ისტორია, ჟურნალი, ჩანაწერები) — ცალკე დოკუმენტებად; დოკუმენტი < 1 MiB.
- **ID**: „ერთხელ“/„უნიკალური“ → განსაზღვრული ID + **create-only** (slot = პირი+თარიღი+უჯრა; payout = lessonId; სივრცე = applicationId). სხვა შემთხვევაში auto-ID.
- **ერთდროულობა**: ტრანზაქცია — ჯერ წაკითხვა, მერე ჩაწერა, პატარა, გარე ზარი შიგნით არასდროს; განახლებისას version/precondition → 412.
- **ცხელი წერტილები**: ერთ დოკუმენტზე ხშირი ჩაწერა (მრიცხველი, „ბოლო მდგომარეობა“) — გაანაწილე ან დააბათჩე; მონოტონურ indexed ველზე ჩაწერა ≈ 500/წმ-მდე.
- **ინდექსები და სიები**: composite ინდექსი კოდშია (`firestore.indexes.json`) + ტესტი; ახალი ფილტრი = ახალი ინდექსი; სია: limit + cursor (startAfter).
- **დენორმალიზება წაკითხვისთვის**: წყარო ცალკეა და ჭეშმარიტია; listing-დოკუმენტს job ანახლებს და აქვს rebuild.
- **ჯამები**: ჯამი/რაოდენობა — Firestore aggregation (count/sum) ან job-ით rollup; ბევრი დოკუმენტის წაკითხვა ჯამისთვის — არა.
- **სქემის ევოლუცია**: `schemaVersion`; ახალი ველი ოფციური + default; მიგრაცია: expand → migrate → contract (იდემპოტენტური სკრიპტი, dry-run).
- **სიცოცხლის ციკლი**: დროებითი მონაცემი (hold, კოდი, deliveries) — TTL; ისტორია (ledger, audit) არასდროს იშლება; backups (PITR) ჩართულია.
- **დრო**: Timestamp UTC-ში; ბიზნეს-თარიღი (დღე) ცალკე ველად Asia/Tbilisi-ში.
- **უსაფრთხოება/ტესტი**: Rules deny-all; PII ლოგში არ გადის; ტესტი Emulator Suite-ზე (repository, ტრანზაქცია, rules, ინდექსები) mock-ის გარეშე; დატვირთვა — k6.

## 5. ბექენდის მოდულები (M1–M8)

სტრუქტურა ყველგან ერთნაირი: `http/` (controller, ვალიდაცია) · `application/` (use case = ერთი პატარა ტრანზაქცია) · `domain/` (სუფთა TS, წესები) · `infrastructure/` (repository→Firestore) · `definition.ts` (declarative განმარტება) · `index.ts` (ერთადერთი საჯარო ინტერფეისი). სხვა მოდულთან — მხოლოდ index.ts-ით.

**ფონური job-ები**: job = Firestore ჩანაწერი იმავე ტრანზაქციაში, რომელიც ბიზნეს-ცვლილებას წერს → Cloud Tasks (ვადა, retry) ან Cloud Scheduler (პერიოდული, ზონა Asia/Tbilisi) → `/internal/jobs/*` იდემპოტენტური handler; ჩავარდნა → failed + alert, არასდროს ჩუმად.
**განმარტება vs ძრავა**: ვადები, ზღვრები, ნაბიჯები, პაკეტის შემადგენლობა, ტექსტები — `modules/<name>/definition.ts` ან config-დოკუმენტი (სქემით, ვერსიული, effective-dated); **ჩანაწერი ინახავს გამოყენებულ ვერსიას/snapshot-ს** (ახალი განმარტება ძველ ჩანაწერს არ ეხება).
**გარე სისტემები**: adapter ყოველ გარე სისტემაზე: timeout; retry მხოლოდ იდემპოტენტურზე; circuit breaker BOG-ზე; ტესტში fake adapter (timeout, დუბლიკატი, გადალაგება).

### M1 · იდენტობა და უფლებები (A1·A7·B1·B4·B5·C7·D1 · STU-01–04,29,33,35 · PAR-01,04,06,17)

- შესვლა: Firebase Auth-ს ჩაშენებულად **ტელეფონი+პაროლი არ აქვს** → ADR-ით აირჩიე custom token ან სინთეტიკური email (B1-ს ეხება; პაროლის აღდგენა უსაფრთხოებისთვის კრიტიკულია). **ADR სჭირდება ჯერ.**
- გვერდზე წვდომა = გუნდის უფლება + პაკეტი; `/me/capabilities` მხოლოდ ნავიგაციისთვის.
- SMS კოდი (6 ნიშანი PAR-04, PAR-06, STU-03): ინახება hash + ვადა + მცდელობები (TTL), ლიმიტის გადაჭარბებისას გაგზავნა იკეტება (მიზეზი: SMS ხარჯი და კოდის გამოცნობა).
- ჩავარდნები: ერთი ადამიანი რამდენიმე სივრცეში (D1 გადართვა) · ინსტრუქტორი სკოლიდან წავიდა · სტუმარი (guest) მხოლოდ წაკითხვა · კოდი ორჯერ · პაკეტი შეიცვალა.
- ტესტები: can() მატრიცა (როლი×მოქმედება×რესურსი) · cross-tenant წვდომა ყველა რესურსზე · კოდის ბრუტფორსი და ვადა · წევრობის დასრულება.
- განმარტებაზე დამოკიდებული: როლები/უფლებათა ნაკრები (#12) → permission-set; კოდის სიგრძე/ვადა/არხი (#13) → config; პაკეტის შემადგენლობა → entitlement ცხრილი; სტუმრის წესები (#1) → config.

### M2 · პარტნიორები: რეგისტრაცია, ავტოპარკი, გუნდი (B2·B3·C2·C3·C8·D6 · PAR-02–05,07,10,14,15,25)

## 6. Front-end

**სტეკი**: Next.js App Router (ვები), React Native (მობილური), TypeScript strict. **მონაცემი**: მხოლოდ გენერირებული api-client + TanStack Query; fetch კომპონენტში არა. **ფორმა**: react-hook-form + zod (სქემები `packages/schemas`; სერვერის 400 ველებზე ებმება). **ტექსტი/დრო/ფული**: i18n კატალოგი; ერთი formatter (Asia/Tbilisi, თეთრი→ლარი). **ფაილი**: signed URL პირდაპირ Storage-ში; გადახდის შედეგი — სერვერის სტატუსით.

წესები:

- ყველა ეკრანი: `loading | empty | error | ready` — discriminated union + exhaustive switch (შეუძლებელი UI მდგომარეობა კომპილაციაზე ჩანს).
- `AppError.code` → ქცევა (`slot_taken` → ალტერნატივები; `hold_expired` → ახალი არჩევა); `retryable` → „ხელახლა ცადე“; `traceId` — მხარდაჭერისთვის.
- ჩაწერა: submit lock + Idempotency-Key; გადახდის/გარე ნაკადის შედეგი — **სერვერის სტატუსით (polling backoff-ით), არა redirect-ით**.
- ვადები/წესები/ნაბიჯები მოდის კონფიგიდან/definition-იდან (GET /v1/config, i18n); უცნობი enum მნიშვნელობა უსაფრთხოდ მუშავდება. ბიზნეს-წესი (ფასი, უფლება, დაბრუნება, გადახდის შედეგი) — სერვერზე.

## 9. CI/CD და Ops

ერთი კონტრაქტი, ერთი პაიპლაინი, სამი გამოშვების გზა — თითოეულს თავისი უკან დაბრუნება.
**PR გეიტები (Cloud Build, ყველასთვის)**: lint+typecheck (strict, no-any, მოდულის საზღვრები) · unit (domain, property-based) · integration (Emulator Suite, ჩავარდნის შემოწმება) · rules+contract (Firestore/Storage rules, OpenAPI diff) · security (dependency, secrets scan).

- **ბექენდი**: build → გეიტები → deploy staging (ახალი revision) → smoke+e2e (Playwright) → prod (traffic split) → rollback (წინა revision).
- **ვები (Firebase App Hosting)**: PR build (types, unit) → staging (ცალკე backend) → e2e → prod rollout (git commit → rollout) → instant rollback (წინა image; ეტაპობრივი გამოშვება დადასტურებული არ არის).
- **მობილური**: PR build (types, unit, Maestro) → internal build (EAS/Fastlane — ADR) → App Distribution → TestFlight/Play internal → store release → Crashlytics (ზღვარი — ADR); უკან დაბრუნება არ არსებობს → kill switch + მინიმალური ვერსია.
- გარემოები: dev (Emulator Suite) · staging (ცალკე პროექტი) · prod (ცალკე პროექტი). ინფრა: Terraform (მინიმალური: Cloud Run, Tasks, Scheduler, IAM; rules/indexes — Firebase CLI, მხოლოდ rules tests-ის შემდეგ). Secrets: Secret Manager, კლიენტში არა.
- წესები: 1 ერთი კონტრაქტი (OpenAPI diff-გეიტი; ძველი აპის ვერსიები მხარდაჭერილია, ვადა — ADR) · 2 სქემის ცვლილება expand→deploy→contract, backfill job dry-run-ით · 3 გამოშვება/უკან დაბრუნება · 4 დატვირთვა და უსაფრთხოება (k6 გაშვებამდე და დიდ ცვლილებებზე; protected branches; secrets scanning; ფულისა და auth-ის კოდზე ორმაგი რევიუ; Claude Code PR-ებზეც იგივე გეიტები).

## 11. შეცვლის ჩეკლისტი (განმარტება იცვლება)

ეს ძრავაა თუ განმარტება? · API იცვლება მხოლოდ დამატებით? · მონაცემის მიგრაცია საჭიროა (expand→migrate→contract)? · ძველი ჩანაწერები ინახავენ ძველ ვერსიას (snapshot)? · კლიენტები უძლებენ უცნობ მნიშვნელობას? · policy ტესტები განახლდა, ინვარიანტის ტესტები უცვლელია? ძრავა (ledger, idempotency, state machine, error model, tenant isolation) იცვლება იშვიათად — ADR + რევიუ. განმარტება — config/definition/i18n. **სამი დონე**: 1 მუდმივი კოდში (declarative ფაილი) — ნაგულისხმევი · 2 config — მხოლოდ თუ საკითხი ღიაა (❓) ან უკვე შეიცვალა · 3 generic rule engine/form builder — **არ ვაშენებთ**.

განმარტება → სად ცხოვრობს: გაუქმების ვადა (STU-24) config (ჩანაწერი ინახავს პოლიტიკის ვერსიას) · სწრაფი ტესტის წესები (#8) config (30·5·30) · პაკეტი 1/2 (PAR-07) entitlement ცხრილი definition-ში · შეტყობინებები (#6,#17) mapping+შაბლონი · რეგისტრაციის ნაბიჯები (#10) step definitions · მარშრუტის წესები ავტო/ხელით (#19) config ფლაგი.

## 12. დანამატი — „Visual Guide“ (14 გვ.)

წყარო: „DriveNet 2027 · ინჟინერიული პრინციპები, არქიტექტურა და პატერნები“ (ვიზუალური ასისტენტი). იგივე 27 პრინციპი და არქიტექტურა, ვიზუალურად; ქვემოთ — რაც v6-ზე მეტია ან განსხვავდება.

- **სამი დონე**: 🔒 ფიქსირებული (27 პრინციპი, მოდულის ფენები, OpenAPI წესები, ფულის/უფლების/ერთდროულობის მექანიზმები, შეცდომის მოდელი) · 🔧 კონფიგურაცია (ვადები, ზღვრები, ნაბიჯები, ტექსტები, პაკეტის შემადგენლობა, kill switch; ჩანაწერი ინახავს ვერსიას) · 🟢 თავისუფალი (ახალი endpoint, use case, ეკრანი, ველი, წესი მოდულის შიგნით).
- **ერთი მოთხოვნის გზა**: JWT → `can()` (principal, workspace) → ვალიდაცია (zod + Idempotency-Key) → use case (ერთი პატარა ტრანზაქცია; „წაკითხვა → ჩაწერა + job ჩანაწერი“) → პასუხი ან AppError (problem+json) → job → idempotent handler → adapter → ჩავარდნა: failed + alert.
- **მოდულებს შორის კავშირი**: M1 ყველას აძლევს principal-ს და უფლებებს · M3 ⇄ M4 (ჯავშანი ← გადახდა; გაუქმება → დაბრუნება) · M2 ⇄ M8 (განაცხადი ← ადმინის დამტკიცება) · ყველა → M7 (მოვლენა → შეტყობინება job-ით).
- **პატერნების კატალოგი** (ახალი ფუნქცია მათგან აიწყობა; ახალი პატერნი — მხოლოდ ADR-ით): Contract-first · მოდულური მონოლითი · Ports & Adapters (M1·M4·M6·M7) · Idempotency-Key (ყველა POST/PUT) · create-only ID (M2·M3·M4·M6·M7) · State machine (M2·M3·M5·M6) · Append-only ledger (M4·M6·M8) · Transactional job (M3·M4·M6·M7) · Listing/წაკითხვის მოდელი (M3) · Policy ფუნქცია `can()` (M1+ყველა) · Declarative definition (ყველა) · Value Object/branded types (Money, ID, Route) · Clock port · Signed URL + CDN (M2·M5).
- **ერთდროულობის სამი ტექნიკა**: (1) განსაზღვრული ID + create-only (პირველი — წარმატება, მეორე → 409 slot_taken); (2) ტრანზაქცია + job ჩანაწერი (ორივე ჩანაწერი ერთად ან არცერთი) ; (3) Idempotency-Key (ორმაგი დაჭერა = ერთი ჯავშანი/გადახდა).
- **Firestore მოდელის 5 წესი**: ერთი ეკრანი = ერთი წაკითხვა · რაც ერთად იცვლება — ერთ დოკუმენტში, ისტორია — ცალკე · root collection + მფლობელის ველი (workspaceId) · ახალი ველი ოფციური + default, `schemaVersion` · მიგრაცია expand→migrate→contract · ჯამი — aggregation ან job-rollup.
- **სენიორ-გადაწყვეტილებები** (შეცვლა — მხოლოდ ADR): ერთი Cloud Run სერვისი (❌ მიკროსერვისები; 🔁 გადასახედი: load-ტესტი ან გუნდის ზრდა) · Firestore deny-all, წვდომა API-ით (🔒) · Cloud Run პირდაპირ, JWT სერვისში (❌ API Gateway; 🔁 Load Balancer + Armor საჭიროებისას) · job = Firestore ჩანაწერი + Tasks/Scheduler (❌ გარე ზარი ტრანზაქციაში, Pub/Sub; 🔁 Pub/Sub — მოვლენების ზრდისას) · ფული: append-only ledger + BOG სტატუსის გადამოწმება (🔒) · Contract-first OpenAPI + გენერირებული api-client (🔒) · ფაილი/ვიდეო CDN+signed URL (🔒) · განმარტება declarative/config-ში, ვერსიით (🔒) · ვები პირველი, მობილური შემდეგ (🔁 მობილურის ფაზაზე) · Monorepo trunk-based, პატარა PR (🔁 გუნდის ზრდისას) · TypeScript strict + zod საზღვარზე (🔒) · მობილური: kill switch + მინიმალური ვერსია (🔒).
- **არასდროს**: თავისუფალი UPDATE სტატუსზე · გარე ზარი ტრანზაქციაში · ფულის ჩანაწერის შეცვლა ან წაშლა · კლიენტის პირდაპირი წვდომა ბაზაზე · ფასის/უფლების გამოთვლა კლიენტზე · PII, ტოკენი, კოდი ლოგში · ციფრის (ვადა, ლიმიტი) ჩაწერა კოდში განმარტების გარეშე.
- **ახალი ფუნქციის გზა (7 ნაბიჯი)**: 1 ფუნქციის ახსნა დეტალებში (ხელით) → 2 აირჩიე მოდული (ახალი — ADR) → 3 endpoint OpenAPI-ში (მხოლოდ დამატებით) → 4 ცვალებადი წესი → definition/config → 5 use case: 1 ტრანზაქცია + job ეფექტზე → 6 ტესტი → კოდი პატარა ნაბიჯებით → 7 გეიტები მწვანე → PR · kill switch რისკზე. ცვლილების გზა: ახალი ველი/endpoint — OpenAPI-ში დამატება (🟢) · ახალი გარე სისტემა — port + adapter + fake (🟡) · ახალი მოდული — ADR + ფენები + index.ts (🟡) · გატეხილი ცვლილება — expand→deploy→migrate→contract (🔴 პირდაპირ არა) · პრინციპიდან გადახვევა — ვჩერდებით, ვკითხულობთ, ADR (🔴).
